## Part A: The Status Map (A1)

| Endpoint | Success Status | Real Failure Statuses | Why Each Status Code Was Chosen |
|---|---|---|---|
| `POST /complaints` | `201 Created` (`200 OK` on idempotent retry) | `400 Bad Request`<br/>`401 Unauthorized`<br/>`422 Unprocessable`<br/>`429 Too Many Requests`<br/>`503 Service Unavailable` | `201` indicates successful resource creation with `Location`. `200` signals cached idempotent repeat. `400` signals malformed JSON. `401` signals missing Bearer token. `422` signals field validation failure. `429` signals rate limit exceeded with `Retry-After`. `503` signals external dependency down and fallback exhausted. |
| `GET /complaints/{id}` | `200 OK`<br/>`304 Not Modified` | `404 Not Found`<br/>`406 Not Acceptable` | `200` delivers payload representation. `304` tells client cached ETag is fresh with zero body bytes. `404` tells caller ID does not exist. `406` tells caller requested Accept mime-type cannot be produced. |
| `GET /complaints` | `200 OK` | `400 Bad Request`<br/>`406 Not Acceptable` | `200` delivers filtered collection array. `400` indicates invalid query string parameter (e.g. unknown category). `406` indicates unacceptable Accept header. |
| `PATCH /complaints/{id}` | `200 OK` | `401 Unauthorized`<br/>`404 Not Found`<br/>`412 Precondition Failed`<br/>`422 Unprocessable` | `200` confirms successful partial update and delivers new ETag. `401` rejects unauthenticated updates. `404` signals missing target. `412` signals ETag mismatch preventing lost updates. `422` rejects invalid field edits. |
| `DELETE /complaints/{id}` | `204 No Content` | `401 Unauthorized`<br/>`404 Not Found`<br/>`409 Conflict` | `204` confirms resource was removed with nothing left to return. `401` rejects unauthenticated caller. `404` signals missing resource. `409` signals state conflict (cannot delete a complaint that is already assigned or in-progress). |
| `POST /complaints/{id}/escalate` | `200 OK` | `401 Unauthorized`<br/>`404 Not Found`<br/>`409 Conflict`<br/>`422 Unprocessable` | `200` confirms escalation applied. `404` signals missing grievance. `409` signals state conflict (already in escalated state). `422` indicates missing escalation reason. |
| `OPTIONS /complaints` | `204 No Content` | — | Returns `Allow: GET, POST, OPTIONS` with CORS headers. |

## Part B: The Type Catalogue (B2)

We defined a stable type catalogue where error URIs are immutable contracts that client applications branch on:

| Stable Type String (`type`) | Status Code | What Triggers It |
|---|---|---|
| `/errors/invalid-request` | `400 Bad Request` | Syntactically malformed JSON body or invalid query parameters. |
| `/errors/unauthorized` | `401 Unauthorized` | Missing or malformed `Authorization: Bearer <token>` on protected endpoints. |
| `/errors/complaint-not-found` | `404 Not Found` | Requested complaint ID does not exist in the repository. |
| `/errors/not-acceptable` | `406 Not Acceptable` | Client demanded an unsupported representation in `Accept` header (e.g. `text/csv`). |
| `/errors/state-conflict` | `409 Conflict` | Action conflicts with current lifecycle state (e.g. escalating already-escalated issue, or deleting in-progress issue). |
| `/errors/precondition-failed` | `412 Precondition Failed` | Stale `If-Match` header during update, preventing concurrent lost updates. |
| `/errors/validation-failed` | `422 Unprocessable Entity` | Well-formed JSON fails domain business constraints; returns field-level `errors[]`. |
| `/errors/rate-limit-exceeded` | `429 Too Many Requests` | Client exceeded 30 requests/minute budget; carries `Retry-After: 60`. |
| `/errors/service-unavailable` | `503 Service Unavailable` | Downstream Accounts service down and asynchronous queue full. |
| `/errors/internal-error` | `500 Internal Server Error` | Unhandled runtime exception; internal details masked safely from client. |

## Part C: Problem Details & Field-Level 422 Errors

### 3. Problem Details Body Breakdown (B1 & B3)

```json
{
  "type": "/errors/precondition-failed",
  "title": "Precondition Failed",
  "status": 412,
  "detail": "Resource has been modified concurrently. Current ETag is \"2-d7b3e4\"; requested was \"1-a8f9c1\". Refresh before editing."
}
```
- **`type` (URI):** Machine-readable stable identifier categorizing the problem. Clients use this to branch programmatic error recovery logic.
- **`title` (string):** Short, human-readable summary of the problem type (constant per type).
- **`status` (integer):** The HTTP status code generated by the origin server for this occurrence of the problem.
- **`detail` (string):** Human-readable explanation specific to this occurrence of the problem, assisting debugging.

## Part D: Answers to Questions 5, 6, and 7

### 5. Which Endpoints are Safe to Retry, and Which Status Codes Tell a Client So?
- **Endpoints Safe to Retry:**
  1. All **GET** endpoints (`GET /complaints/{id}`, `GET /complaints`) - naturally safe and idempotent.
  2. All **DELETE** endpoints (`DELETE /complaints/{id}`) - idempotent (deleting an already deleted record yields 404/204 without side-effects).
  3. Conditional **PATCH** endpoints carrying `If-Match` - state-guarded idempotent write.
  4. **POST** endpoints carrying an `Idempotency-Key` - made retry-safe by the server's deduplication cache.
- **Status Codes Indicating Retry Safety:**
  - `429 Too Many Requests` with `Retry-After: 60`: Tells client the request was valid, but client must pause and retry after the specified seconds.
  - `503 Service Unavailable` with `Retry-After`: Indicates transient server overload or maintenance; safe to retry with exponential backoff.
  - `504 Gateway Timeout`: Transient network timeout; safe to retry if the operation is idempotent.
  - *(Crucial Rule: Status codes `400`, `401`, `404`, and `422` must NEVER be retried unchanged; they represent deterministic client errors).*

### 6. Mapping Internal Errors to Clean Client Errors (B4)
- **Where Mapped:** In the global error middleware in `src/app.js`:
  ```javascript
  app.use((err, req, res, next) => {
    console.error('[SERVER ERROR]:', err);
    return problem(
      res,
      500,
      'internal-error',
      'An unexpected internal error occurred. The incident has been recorded.'
    );
  });
  ```
- **What Was Hidden From The Caller:**
  We hid the raw Node.js runtime stack trace, local directory file paths (`c:\Users\...\src\store.js:42`), internal memory pointers, database connection strings, and low-level system error messages. Leaking stack traces or SQL/NoSQL driver errors is a serious security vulnerability that aids attackers in fingerprinting server infrastructure. The full technical diagnostics are logged exclusively server-side.
